# 产品定位与设计

## 定位与目标

Rig 是为维护者自身需求开发的开源个人 Agent harness。本地运行，通过对话接受工作委托，自主完成通用个人任务与编程任务。它追求好用、精简但足够用，允许维护者长期调整提示、执行环境和外围能力，逐步形成自己的 AI 工作环境。

当前目标用户是维护者本人，其他开发者的采用方式不构成设计约束。通用个人任务优先于编程任务，内核保持任务中立，不内置具体业务流程。

项目同时承担实际使用、学习 Agent 开发和积累未来 AI 产品基础能力的目标。取舍以维护者的真实需求为依据；可复用性从使用与改造中积累，不为尚未出现的需求预建通用框架。

维护者选择 Rig 的理由是能够掌握、调整和持续维护自己的 Agent。它是否更适合某项工作，通过与现有产品的实际使用比较判断，不提前宣称更智能或更通用。开源是发布方式，不意味着必须承担社区通用需求。

仅支持 macOS 和 Linux，永不支持 Windows；采用 MIT 许可证。工程现状与技术边界见[架构](architecture.md)。

## 使用方式

CLI 负责启动与管理，Web UI 是首个主要交互入口。每项工作通过对话发起，保留用户意图、Agent 的交互输出、后续修正和成果入口。

完整流程是：

1. 用户描述目标，按需提供资料、工作区和约束。
2. Agent 在授权范围内自主规划与执行；缺少关键信息或需要授权时，向用户询问。
3. 用户检查结果，通过同一对话补充信息、修正目标或继续工作，也可以停止执行。
4. Agent 交付实际成果；文件成果支持预览、保存和下载。重新打开会话后，用户能够查看历史并继续工作。

资料分析、代码阅读和文件创建或修改共享这一流程，成功标准由具体委托决定。产品定位不绑定某个行业或个人业务场景。

## 自主执行与用户控制

默认自主程度较高，不要求用户逐步下达指令或强制批准每份计划。自主执行限定在用户委托的工作内；当前不主动发现需求或自行发起新任务，这类能力留给未来外围扩展。

执行权限与审批策略分别表达：

| 模式 | 执行范围与审批 |
| --- | --- |
| 安全模式 | 用户选定的资料目录只读，成果区域可写。 |
| 受保护模式，默认 | 工作区内普通操作自主执行。访问额外目录、以 root 等更高系统权限执行，以及识别出的关键危险操作，需由用户批准。 |
| Full access | Rig 层面默认允许执行和系统提权，不做逐次工具审批；实际权限与保护由操作系统、外围进程或 sandbox 决定。 |

受保护模式允许申请扩大目录范围，也允许申请系统提权。一次批准仅授予批准的操作与范围，不隐含切换为 Full access。扩大目录授权与获得更高系统权限是不同的权限变化。

第一版由用户审批，不引入自动审查。减少重复审批是体验要求，可以复用范围与条件一致的已有授权；具体匹配、有效期与撤销方式交给后续设计。危险识别不能替代实际执行隔离，也不承诺完整识别任意命令或脚本的破坏性行为。Rig 的批准不能替代操作系统认证。

用户检查成果、依据和授权属于产品体验。debug、trace 和运行评估属于开发与运营支撑，不以展示大量执行日志作为核心产品价值。

## 改造与个人工作环境

维护者可以按需要调整 system prompt，适配常用模型与基础设施，改善执行环境，并持续维护有方向的外围工具或插件。具体能力由底座还是外围封装承担，根据真实需求决定，不提前设计固定任务分类或工作流。

重点探索两个产品方向，其交付阶段尚未确定：

- 跨客户端完整参与工作。工作事实、成果和关键交互不因客户端变化而缺失；只有远端客户端时，也能完成关键使用过程。不同设备可以采用不同布局和输入方式，不依赖第三方聊天渠道转发部分能力。
- 知识持续参与执行。Agent 能通过对话帮助用户提炼知识，保存到人类可读、可检查和可修正的仓库；后续按需自动使用，并把实际采用的知识作为来源呈现。知识的时效与修正需要影响后续使用。

任务结束后的知识沉淀对话是可选流程，不是每次任务的必经步骤。自动使用知识不要求逐条审批，也不意味着知识永远正确。索引、检索与入库机制留给后续设计。

## 首个功能 milestone

用户能够通过对话委托 Agent 创建并迭代文件成果，完成执行、预览、对话修改、保存和下载的完整体验。以“鹈鹕骑自行车”的 SVG 动画作为端到端验收用例。

验收标准：

- 交付真实 SVG 文件，预览能够辨认鹈鹕骑车，并呈现持续动画。
- 用户在同一对话中提出修改，Agent 更新成果；预览、保存和下载的内容对应用户选择的成果。
- 会话保留请求、交互和成果入口，用户能够再次打开并继续工作。
- 用户能够停止执行；需要授权时，执行按当前模式等待或处理用户决定。

这一用例验证委托与成果交付，不代表综合编程能力评测。首个 milestone 不要求完整远程访问、知识管理、通用插件系统、主动任务发现或自动配置优化，也不据此宣称已经满足所有通用任务与现有仓库开发需求。

## 能力评测

早期尝试使用公开 benchmark 检查基础能力，包括 [SWE-bench](https://www.swebench.com/) 和 [Terminal-Bench](https://www.tbench.ai/)。具体版本、任务子集、运行环境和评估方式在开发与 Runtime 研究中确定。

评测结果同时受模型、提示、工具、执行环境和 harness 影响，比较时应记录这些条件及执行成本。公开基准用于检查能力，完整使用体验仍通过实际使用与验收判断。

早期不建设私有 benchmark。需要时再根据实际使用中的问题讨论，具体业务任务不固化为产品定位或底座内置流程。

## 对 Runtime 设计的要求

- 同一执行基础支持通用个人任务与编程任务，不依赖固定业务流程。
- 执行事实与生命周期由内核拥有，客户端和展示层不独立维护业务状态；浏览器刷新不决定任务生命周期。
- 会话历史、模型上下文、执行记录与展示数据解耦，支持用户检查、继续、干预和停止工作。
- 提示、工具和执行环境能够按需调整，并落实所选权限与用户授权；不提前规定扩展机制。
- 保留调试与逐步追踪执行动作的能力，为模型、提示和 harness 的比较提供开发支撑。

Runtime session 继续讨论模型接入、Agent Loop、上下文管理、工具执行、权限隔离及审批复用、会话持久化与中断恢复，以及外围能力接入。跨客户端访问和知识融合应遵守上述产品原则，具体机制与交付范围另行设计。
